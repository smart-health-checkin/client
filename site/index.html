How a check-in runs

Try the demo

The demo is a fictional clinic's check-in page running the real protocol stack. Pick a scenario from the demo bar (insurance card, new-patient summary, day-of PHQ-2, allergy review, med list), press Check in with your health app, and watch the response come back, get verified, and post to a public test FHIR server. Every technical artifact — the SMART request, the wallet's response, the FHIR transaction, the server's reply — is one click away in the Developer detail section.

  • No wallet-equipped phone? Add mock=1 to the URL fragment — a built-in mock wallet answers with fabricated demo data over the real CBOR/COSE/HPKE pipeline: demo/#mock=1&submit=dry-run
  • The autofill pattern: the allergy-review example shows a provider form literally prefilled from the patient's app — request USCDI data, populate the form inline, let the patient annotate.
  • Everything is a URL. The whole configuration — scenario or full request object, patient, FHIR target, return leg — lives in the URL fragment, so any test case is a shareable link (grammar).

Quick start for EHRs and portals

Two integration shapes, both closed-loop — the response returns to your page, and your backend only ever sees ordinary FHIR. The URLs below point at this deployment's hosted builds, so the snippets work as-is for experimentation; vendor a pinned copy for anything real.

1. Ask, await, prefill. Define the request inline (the kit fills in protocol boilerplate), await the patient's validated response, and populate your own form — no submission, your code stays in control:

<script type="module">
  import { requestCheckin }
    from "";

  const response = await requestCheckin({
    purpose: "Review your allergy list before your visit",
    items: [{
      id: "allergies",
      title: "Allergies and intolerances",
      content: {
        kind: "selection.fhir",
        profiles: ["http://hl7.org/fhir/us/core/StructureDefinition/us-core-allergyintolerance"],
      },
      accept: ["application/fhir+json"],
    }],
  });
  // response.artifacts → prefill your intake form inline
</script>

2. Drop-in element: collect and submit to your FHIR server. The element launches the flow, verifies the response, POSTs a transaction Bundle (with Provenance) to your server, and sends the patient to your next step. Define your request with registerScenario(...) or a request-json attribute:

<script type="module">
  import { registerScenario }
    from "";
  registerScenario("visit-prep", { purpose: "…", items: [ /* … */ ] });
</script>

<smart-checkin
  scenario="visit-prep"
  patient="Patient/123"
  fhir-base="https://your-fhir-server.example.org/r4"
  return-url="/checkin/payment">
</smart-checkin>

The full walkthrough — attributes, events, the JS API, auth wiring, and the production checklist — is in the integration guide.
